# P0 改造方案：网页端鉴权 + 审计日志

> **状态：已实现并全绿（2026-09-20）**。验收结果见文末「实现记录」一节。
> 目标：让 AirNav-Agent 从「能演示」变成「可被信任」。
> 范围：`agent/web/server.py` 及其前端；**不改** `agent/agent_loop.py` 与工具层。
> 前置约束（沿用项目铁律）：不新增依赖、不改 V1 源目录、不保存密码明文。

---

## 1. 为什么是这两件事

现状（2026-09-20 核对代码）：

| 面 | 现状 | 证据 |
|---|---|---|
| 网页 Agent | **零鉴权**，任何人都能提问、拉产物 | `agent/web/server.py` 五个路由无任何校验 |
| 后端 Job API | 已有 API Key 雏形 | `backend/api_server.py` 的 `TOKEN = os.getenv("API_TOKEN","")` + `Depends(auth)` |
| 审计 | **完全没有** | 网页侧每次运行只推 SSE，不留痕；后端只有 job 级 `pipeline.log` |

医疗场景里，鉴权与审计追踪是**准入线**而非加分项：谁在什么时候、对哪个病例、问了什么、
系统调了哪些工具、给出什么结论、用的哪个模型版本，必须可回溯。
两件事合计约 **550 行、零新增依赖、1.5~2 天**，是投入产出比最高的一步。

## 2. 鉴权方案

### 2.1 为什么不能照搬后端

后端用 FastAPI 的 `APIKeyHeader` + `Security`；网页版是 **starlette**（本机没有 fastapi，
这是既有技术决策）。因此鉴权要用 **starlette 中间件**手写，约 40 行，不引入新依赖。

### 2.2 凭据模型（先做单凭据，P1 再上用户表）

```bash
AIRNAV_API_TOKEN=<随机 32 字节 hex>      # 空 = 关闭鉴权（本地开发默认不变）
AIRNAV_WEB_COOKIE_SECURE=1               # 仅当挂在 HTTPS 反代后
AIRNAV_WEB_ACTOR=qc                      # 可选：单凭据下的操作者标识（写进审计）
```

- **向后兼容**：新名 `AIRNAV_API_TOKEN` 优先，回落后端旧名 `API_TOKEN`，两个面共用一套凭据。
- **禁止硬编码**：token 只从环境变量读；仓库内不落盘（沿用「不保存密码」铁律）。

### 2.3 携带方式（两种，覆盖程序与浏览器）

1. **`X-API-Key` 头** —— 脚本 / `probe_web.py` / 后续监控探针；
2. **`airnav_token` HttpOnly Cookie** —— 浏览器。首次访问 `/login` 提交 token 换 Cookie
   （表单 POST，`SameSite=Lax` 防 CSRF），成功后 **303** 回 `/`（PRG 模式：
   浏览器改用 GET 回首页，刷新不会重复提交）。

校验用 `hmac.compare_digest`（防时序侧信道），失败返回 401 + 写一条审计。

### 2.4 白名单（必须放行）

`/health`（监控探活打不进来就是自断可用性）、`/login`、`/static/*` 里的登录页资源。
`/artifacts/<name>` **必须鉴权** —— 三维视图含真实病例解剖，是敏感数据。

### 2.5 改动清单

| 文件 | 改动 | 量 |
|---|---|---|
| `agent/web/auth.py` | 新增：中间件 + 登录路由 + token 解析 | ~120 行 |
| `agent/web/server.py` | 挂中间件、加 `/login` 路由、`/api/chat` 记录 actor/ip | ~30 行 |
| `agent/web/static/index.html` | 401 时显示登录框，成功后重试原请求 | ~30 行 |
| `agent/scripts/check_web.py` | 新增鉴权用例：无 token→401、带 token→200、`/health`→200 | ~40 行 |
| `agent/scripts/probe_web.py` | 加 `--token` 参数 | ~5 行 |

### 2.6 验收标准

- [x] 未带凭据访问 `/api/chat`、`/artifacts/*` → **401**，响应体不含任何病例信息
- [x] 带 `X-API-Key` 或 Cookie → 正常 SSE 流
- [x] 未带凭据访问 `/health` → **200**（探活不受影响）
- [x] 未设置 `AIRNAV_API_TOKEN` 时行为与今天完全一致（本地开发零摩擦）
- [x] `check_web.py` 新增用例全绿；`probe_web.py --token` 能打通

## 3. 审计日志方案

### 3.1 埋点位置：服务端，不碰内核

`NavAgent` 已有 `on_event` 回调与 `AgentRun.to_dict()`（服务端现在就在推 `{"type":"run"}`）。
**审计写在 `agent/web/server.py` 的 worker 收尾处**，agent 内核零改动 ——
保持既有约定「观测层不该有能力弄坏控制流」。

### 3.2 一条记录长什么样

```json
{
  "run_id": "9f2c…", "ts_start": "2026-09-20T14:03:11+08:00", "ts_end": "…",
  "actor": "qc", "client_ip": "203.0.113.20", "user_agent": "Chrome/…",
  "question": "LIDC_0089 3 号候选 1.5mm 器械能不能到？",
  "backend": "gpu41", "model": "qwen2.5:14b", "max_steps": 8,
  "device_diameter_mm": 1.5, "device_margin_mm": 0.2,
  "case_ids": ["LIDC_0089"],
  "steps": [
    {"step": 1, "tool": "plan_route", "args": {"…": "…"}, "ok": true, "elapsed_ms": 8123}
  ],
  "artifacts": [{"file": "viewer_LIDC_0089_c3_d1.5.html", "sha256": "ab34…"}],
  "answer_sha256": "77c1…", "answer": "…原文…",
  "verdict": "ok", "error": null,
  "prev_hash": "…", "hash": "…"
}
```

要点：

- `artifacts` 带 **sha256** —— 事后能证明「当时看的确实是这一版视图」；
- `steps` 来自 `ToolCallRecord`（脱敏：只留工具名、参数、耗时、成败，不留几何大对象）；
- `answer` 留原文（医疗追溯需要），若走隐私模式则只留 hash + 关键字段。

### 3.3 存储：JSONL + 哈希链（P0 不上数据库）

- 路径：`outputs/audit/audit-YYYY-MM-DD.jsonl`，一行一条，天然 append-only；
- 每行带 `prev_hash`（上一行 sha256）→ 形成**哈希链**，改任何一行后续校验必然失败；
- 为什么不上 SQLite：单机并发低，审计要的是「不可改 + 可追溯」，JSONL 更简单；
  schema 已按关系模型设计好，**P1 迁 SQLite/Postgres 时只换写入端**。

### 3.4 配套三个小工具（都在 `agent/scripts/`）

| 脚本 | 作用 |
|---|---|
| `audit_query.py` | 按日期 / 病例 / actor 查询，导出 CSV |
| `audit_verify.py` | 校验哈希链完整性，返回 0/1（可进 CI） |
| `audit_prune.py --days 1825` | 按保留策略归档（**默认只演算，`--apply` 才动文件**；归档前先验链，链坏了拒绝搬 —— 否则「归档」会变成帮人把被篡改的证据收进抽屉） |

### 3.5 改动清单

| 文件 | 改动 | 量 |
|---|---|---|
| `agent/audit/store.py` | 新增：写 JSONL + 哈希链 + 脱敏 | ~150 行 |
| `agent/web/server.py` | worker 收尾调用 `store.record(...)` | ~20 行 |
| `agent/scripts/audit_query.py` | 查询/导出 | ~60 行 |
| `agent/scripts/audit_verify.py` | 链校验 | ~50 行 |
| `agent/scripts/audit_prune.py` | 保留策略 | ~40 行 |
| `agent/scripts/check_audit.py` | 自检：写→读→篡改必被检出 | ~80 行 |

### 3.6 验收标准

- [x] 网页提一次问 → 当日 JSONL 出现**一条**完整记录（含 steps / artifacts / 模型版本）
- [x] `audit_verify.py` 全绿；**手动改一行后校验必然失败**（自证防篡改能力）
- [x] `audit_query.py --case LIDC_0089` 能捞出所有相关运行
- [x] 审计写入失败**不影响** Agent 回答（与 `on_event` 同一原则：观测层不得弄坏控制流）
- [x] `check_audit.py` 进常驻自检清单 → 门禁从 9 套变 **10 套**

## 4. 风险与取舍

| 风险 | 处理 |
|---|---|
| 单 token 不是多用户方案 | P0 明确只做「可鉴权 + 可追溯」；用户表/RBAC 属 P1，schema 已预留 `actor` |
| Cookie + SSE 的 CSRF | `/api/chat` 是 GET 只读触发，Cookie 设 `SameSite=Lax` 即可；写操作留到 P1 再引入 CSRF token |
| 审计文件无限增长 | 按天切片 + `audit_prune.py` 保留策略，配合磁盘水位告警 |
| 审计内容含患者信息 | 病例 ID 本身是假名；`AIRNAV_AUDIT_REDACT=1` 时只存 question 的 hash |
| 反向代理后拿不到真实 IP | 读取 `X-Forwarded-For` 首段，并在文档里注明信任边界 |

### 6.3 自检抓出的两个真 bug（这就是自检存在的理由）

1. **登录页直接 500**。`_html()` 返回的是**字节键**的响应头，外层 `dict()` 一下看起来
   「也能用」，但 Starlette 的 `MutableHeaders` 只吃 str 键。
   → 改成 str 键字典。**这个 bug 光看代码很难看出来**，是 `check_web` 打了一发
   `GET /login` 才暴露的。
2. **登录 Cookie 流程测不到**。`urllib` 默认跟随重定向，而 **303 那个响应自身的
   `Set-Cookie` 在重定向链里被丢掉了** —— 断言全报「没种下 Cookie」，看起来像服务端
   没写 Cookie，实际是测试端拿错了响应。
   → 加了一个不跟随重定向的 opener，直接看 303。

### 6.4 本机 DLP 的坑（改前端之前必读）

本机数据防泄漏按**写入方**决定落盘形态：用编辑器直接写 `agent/web/static/index.html`
会落成 8192 对齐的 `%TSD-Header-###%` 密文，**连 Python 都解不开** ——
而服务端正是用 Python 读这个文件发给浏览器的（页面直接废掉），`git diff` 变成 `Bin`。

→ 前端改动一律走**脚本化落盘**：`agent/scripts/_patch_web_auth.py`（读明文 →
五个锚点替换 → 断言全命中才写，一条没命中就整体放弃，不写半截文件）。
改完必须过三条验收：`git diff --stat` 不是 `Bin`；Python 能 `decode('utf-8')`；
node 能读到明文。完整读写矩阵见 `使用指南.md` §3.6。
