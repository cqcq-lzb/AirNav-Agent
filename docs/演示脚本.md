# 5 分钟演示脚本

> 目标：**不用解释就能照做**。每一拍都给可直接粘贴的命令，以及「屏幕上应该看到什么」。
> 所有命令都实跑验证过（2026-09-28，`--backend gpu41` = qwen2.5:14b / H100）。
> 时间栏是实测值，不是估计。
>
> **演示产物不需要预先准备**：下面引用的 `viewer_*.html` 都是**当场生成**的
> （实测：删掉后重跑，1 832 105 字节逐字节重建）。
> 所以干净 clone 的仓库也能跑完全程 —— 不依赖任何未入库的大文件。

## 演示前 30 秒（只做一次）

```bash
cd /d/AirNav-Agent
set PY=.venv-mcp\Scripts\python.exe
%PY% -m agent.cli doctor --backend gpu41
```

**应该看到**：`可达。可用模型 1 个` + `自检通过。`

> ⚠️ 如果看到「降级运行：推理后端不可用」——
> Web/CLI 仍会启动，但**依赖模型判断的拍子会失败**。
> 先把后端弄起来：`ssh gpu41` → `~/ollama/start_ollama_gpu41.sh`。

## 第一拍｜它知道病例里有什么（约 15s）

```bash
%PY% -m agent.cli ask --backend gpu41 "LIDC_0089 有几个候选？"
```

**应该看到**：`病例 LIDC_0089 有 4 个结节候选。` + `2 步 / 1 次工具调用 / 11.0s`

**要讲的一句话**：这不是模型背下来的 —— 它调了 `list_nodule_candidates`，
数字来自工具返回体。**结论的出处可追。**

---

## 第二拍｜每步工具调用都看得见（约 20s）

```bash
%PY% -m agent.cli ask --backend gpu41 --verbose "LIDC_0089 的 3 号候选能过 1.5mm 器械吗？"
```

**应该看到**（实测）：

```
  [step 1] -> plan_route({'case_id': 'LIDC_0089', 'candidate_id': 3,
                          'device_diameter_mm': 1.5, 'device_margin_mm': 0.2,
                          'profile': 'balanced'})
```

最后是规划数值。**这一步是 1 次工具调用** —— 模型直接选了 `plan_route`，
没有多余试错（这正是「工具描述里写明 `plan_route` 才是结论权威来源」的效果）。

**要讲的一句话**：`--verbose` 把 ReAct 的每一步摊开 ——
**没有黑箱**：每一步都能指出是哪个工具、带了什么参数算的。
参数是**模型填的**（`candidate_id: 3` 不是我们硬塞的），
所以「它有没有理解问题」当场可见。

---

## 第三拍｜拿到带三维视图的报告（约 15s）

```bash
%PY% -m agent.cli ask --backend gpu41 "LIDC_0089 的 3 号候选能过 1.5mm 器械吗？给出路径和三维视图"
```

**应该看到**（实测值）：

| 项 | 值 |
|---|---|
| 路径长度 | **216.24 mm** |
| 最窄直径 | **5.92 mm** |
| 最大转角 | 85.64° |
| 安全余量 | **2.01 mm** |
| 分叉序列 | S163 > J78 > S107 > J53 > S110 > J55 > S114 |
| 产物 | `outputs\viewers\viewer_LIDC_0089_c3_d1.5.html` |

**当场打开那个 HTML**（三维视图，可旋转缩放）。

**要讲的一句话**：报告里的数字**不是模型写的**，是 `plan_route` 的返回体；
模型只负责把结论讲清楚。**算法内核与 V1 逐位一致**（有硬门禁拦着）。

---

## 第四拍｜改一个参数，看结论真的变（约 15s）

```bash
%PY% -m agent.cli ask --backend gpu41 "LIDC_0089 的 3 号候选换成 5mm 器械还能过吗？"
```

**应该看到**：仍然可达，但**最窄直径仍是 5.92mm，余量从 2.01mm 掉到 0.258mm**，
产物换成 `viewer_LIDC_0089_c3_d5.html`。

**要讲的一句话**：同一个候选、同一套内核，**只改器械外径，余量就收紧到 0.258mm** ——
这正是临床上「选多粗的镜子」的真实取舍。**参数一变，产物名也跟着变**
（`_d1.5` → `_d5`），因为产物名带上了影响内容的参数 ——
避免「拿旧图当新结论」。

## 收尾（约 30s）：三条能讲的故事

指向 `docs/一页纸.md §五`，挑一条展开。三条都是同一形状：
**先看到一个假象 → 用物理事实推翻 → 修好 → 加一条会失败的哨兵。**

- **`localhost:11434` 其实是服务器** —— 判据：本机只有 7b，看到 14b 就是转发
- **`.get()` 把「字段名写错」伪装成「这个数据没有」** —— 死代码，界面照常绿
- **评测分数是抽签** —— 同代码三个口径三个数（93.3 / 83.3 / 91.1）

## 附：现场可能踩的三个坑

### 坑 1｜**追问时不要用「同一候选」这种指代**（必读）

实测：

```bash
# ❌ 会答错候选 —— 模型自己挑了个 2 号
%PY% -m agent.cli ask --backend gpu41 "同一候选换成 5mm 器械还能过吗？"
#    答：5mm 器械无法通过编号为 2 的候选结节

# ✅ 显式点名候选编号
%PY% -m agent.cli ask --backend gpu41 "LIDC_0089 的 3 号候选换成 5mm 器械还能过吗？"
#    答：3 号候选 5mm 可达，余量 0.258mm
```

`repl` 模式里同样成立：**「它 / 同一候选 / 刚才那个」这类指代不要在演示中用**。
根因是「候选编号口径」——服务端 1 号与客户端显示编号不一定同一个，
项目里专门有 `id_mapping` 处理，但**演示时点名最稳**。

### 坑 2｜`--include` 是精确匹配，中文 id 不要内联进 shell

```bash
# ❌ 选不到任何用例（精确匹配失败）
%PY% -m agent.scripts.run_eval --include E13
# ✅ 用别名脚本，或写完整中文 id
```

### 坑 3｜别拿单次评测分数当能力数字

```bash
%PY% -m agent.scripts.run_eval --backend gpu41 --repeat 3
```

单次是抽签（实测同代码 93.3% / 83.3% / 91.1%）。
**报「用例级（3 次全过）」+「尝试级通过率」**，两者都有了才算说清口径。
