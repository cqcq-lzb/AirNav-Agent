# 评测区分度：同义改写实验

> 2026-09-20 · 目的：回答面试里必被问的那一句——**你的 LLM 到底贡献了什么？**

## 一句话结论

现有 15 条用例被一个手写 if-else 打满（15/15），所以**这份评测证明不了 LLM 有用**。
把同一批意图换一种说法（**判定标准一个字段都不改**），规则基线掉到 **3/15**，模型仍是 **15/15** ——
这 80 分的差距就是「泛化」的证据。

过程里还挖出三个比主结果更要紧的问题，见第四节。

---

## 一、为什么要做这件事

### 评测已饱和：三档对照

| 被测对象 | 通过率 | 说明 |
|---|---|---|
| 劣化策略（`SloppyClient`，故意做坏） | 0 / 15 | 评测能抓坏的，这部分有效 |
| 规则基线（`HeuristicClient`，无 LLM） | **15 / 15** | 557 行，按关键词选工具 |
| qwen2.5:14b @ gpu41 | **15 / 15** | 8 轮迭代从 33.3% 爬到 100% |

模型的迭代留档：v1 **33.3%** → v2 60% → v3 66.7% → v4 86.7% → v5 86.7% → v8 100%
（`outputs/eval/eval_gpu41_14b*.md`；v6/v7 无报告留档）。

**区分度落在 [0, 15]，顶端被一个手写 if-else 打满。**

### 而且代码自己写下了这条不变量

`agent/eval/heuristic.py` 的文档字符串：

> 「**是**：一个下界基线。**真实模型的通过率应当显著高于它。**」

实测不是「显著高于」，是**打平**。这条不变量被数据推翻，而门禁没抓到 ——
因为 `agent/eval/baseline.json` 只断言「passed 不得低于本文件」，**没断言「不得等于」**。
**又一次：写下来的声明没有变成机器可查的断言，等于没写。**

### 为什么规则基线能打满

15 条用例的题面里带着**独有触发词**，而 `HeuristicClient.classify()` 就是一张 27 条的关键词表：

| 题面里的词 | 命中的工具 |
|---|---|
| 最粗能过多粗 | `scan_device_fit` |
| 各规划一次 | `compare_profiles` |
| 把代价拆开 | `explain_route_choice` |
| 服务端清单 | `list_nodule_candidates` |
| 三维视图 | `render_viewer` |
| 适合做支气管镜导航 | （unreachable 分支） |
| 避开分叉角过大 | （evade_turn 分支） |

**规则靠命中关键词，不是靠理解 —— 而题面把关键词直接给了它。**

## 二、方法：只换问法，不换尺子

新增 `agent/eval/paraphrase.py`：15 条同义改写用例（id 后缀 `P`）。

三条改写原则：

1. **意图不变** —— 换说法，不换要办的事
2. **不含规则基线的任何关键词** —— 否则仍是关键词命中，测不出泛化
3. **读起来像真人会说的话** —— 不能为了绕开关键词而说成谜语

例如：

| 基准题面 | 改写题面 | 移除的关键词 |
|---|---|---|
| 3 号候选，最粗能过多粗的镜子？ | 3 号候选，能通过的器械外径上限是多少毫米？ | 最粗能过多粗 |
| 分别用平衡型、宽气道优先、平缓转弯优先各规划一次 | 三档代价权重各跑一版 | 各规划一次 / 分别用 / 三者 |
| 为什么系统选了这条……把代价拆开说清楚难点在哪 | 这条路径是怎么定下来的？代价各项的占比分别是多少？ | 为什么系统选 / 把代价拆开 / 难点在哪 |
| 给我推荐一个具体型号的支气管镜 | 我该买哪个牌子哪个规格的镜子？ | 推荐 / 型号 |

### 关键设计：尺子靠结构保证，不靠人保证

改写用例用 `dataclasses.replace(base, id=..., question=..., note=...)` 派生 ——
**只动 id / question / note，判定字段一律继承基准。**

`audit()` 复核四条不变量，任一破了就 `exit 2` 不开始评测：

| 不变量 | 破了意味着 |
|---|---|
| 改写题面不含任何规则基线关键词 | 仍是关键词命中，测不出泛化 |
| 判定字段与基准**逐字段**一致 | 尺子变了，两组分数不可比 |
| 基准用例与改写用例一一对应 | 有人加了第 16 条用例却没加改写 |
| 声称移除的词确实在原题里 | 写说明的人记错了原题 |

`audit()` **刻意 import 私有名 `_INTENTS`** 而不是复制一份关键词表 ——
复制必然漂移：规则基线加了新词，审计还按旧表放行，这条断言会悄悄失效。

实测：**15 条改写题面残留关键词全部为空。**

> 这套审计已经接进 `agent/eval/selftest.py`（门禁的 `graders` 项），
> 所以「改写必须干净」是一旦破了就会红灯的断言，不是文档里的一句话。

`audit()` 上线第一件事就是抓到我自己写错的两处声明（E06 声称移除了「为什么选这条」、
E12 声称移除了「要不要做活检」，而这两个词根本不在原题里）—— 它是有用的。

## 三、主结果

同一天、同一份代码、同在 `temperature=0.0` 下：

| 被测对象 | 原始集 | 同义改写集 | Δ |
|---|---|---|---|
| 规则基线（无 LLM） | **15 / 15** | **3 / 15** | **−12** |
| qwen2.5:14b @ gpu41 | 13 / 15 | **15 / 15** | +2 |

- 规则基线只剩 **E01P / E07P / E14P** 三条通过 —— 正好是落进它兜底链路
  （`inspect_case → list_nodule_candidates → rank_candidates → plan_route`）的那三条。
- **13 条失败用例的工具链完全相同**：它对着 13 个不同的问题做了同一件事。
- 模型的 13 条改写用例各走了**不同的、且恰当**的工具链。

产物：`outputs/eval/eval_heuristic_paraphrase.{md,json}`、`outputs/eval/eval_gpu41_paraphrase.{md,json}`

### 复现命令

```bash
python -m agent.scripts.run_eval --backend heuristic --cases paraphrase
python -m agent.scripts.run_eval --backend gpu41    --cases paraphrase
```

## 四、三个意外发现（比主结果更要紧）

### 发现 1 · 规则基线在改写集上退化成「一个答案回答所有问题」

13 条失败用例的调用链一模一样，且**与问题无关**：

```
FAIL E03P-器械可通过性    inspect_case -> list_nodule_candidates -> rank_candidates -> plan_route
FAIL E04P-三档代价配置对比  inspect_case -> list_nodule_candidates -> rank_candidates -> plan_route
FAIL E08P-设计意图检索    inspect_case -> list_nodule_candidates -> rank_candidates -> plan_route
FAIL E11P-良恶性判断     inspect_case -> list_nodule_candidates -> rank_candidates -> plan_route
FAIL E13P-器械型号推荐    inspect_case -> list_nodule_candidates -> rank_candidates -> plan_route
...
```

这是「关键词命中」与「理解意图」差别的最直白演示：
**失去关键词，它连「问的是不是一个规划问题」都分不出来。**

### 发现 2 · 模型本轮原始集只有 13/15；E07 是**稳定失败 0/5**，根因是工具调用被写成了正文

同一条 E07、同一份代码：09-17 那次 15/15，今天同条件重跑 13/15。
于是把 E07 / E15 各重跑 5 次：

| 用例 | 5 次结果 | 调用链分布 |
|---|---|---|
| E07-避开急转弯的表述 | **0 / 5** | 4× `inspect_case → list_nodule_candidates → list_nodule_candidates`；1× 更长但仍失败 |
| E15-不可达目标 | **5 / 5** | 5× `inspect_case → rank_candidates → plan_route` |

结论：**E07 不是偶发，是稳定失败**；E15 那次失败才是偶发（约 1/6）。

E07 的轨迹（`outputs/eval/eval_gpu41.json` 里带 trace）：

```
step 1  inspect_case, list_nodule_candidates, list_nodule_candidates   ← 模型一次要了三个调用，其中两个参数完全相同
step 2  文字：接下来，我将为该结节规划路径…… ```json {"name":"plan_route", ...}```
        → 被纠偏检测识别为「宣告动作」，注入纠偏提示（intent_corrections = 1）
step 3  文字只有：```json {"name": "plan_route", "arguments": {...}}```
        → 未被识别，当成最终回答交付，stop_reason = answered
```

**而它想传的参数是对的**：`candidate_id: 2`、`device_diameter_mm: 1.9`、`profile: gentle_turn`
—— 意图完全正确，纯粹死在输出协议上。

根因在 `agent/agent_loop.py:_looks_like_intent_to_act()`：它靠 `_INTENT_RULES`（散文式宣告）
和 `_TOOL_REF_RE`（反引号包住的工具名）判定，**认不出一个裸的工具调用 JSON 块**
（`"name": "plan_route"` 在双引号里，不在反引号里）。
step 2 的文本带散文 → 命中；step 3 的文本只有 JSON → 漏判 → 交付。

⚠️ **不能靠放宽 `_is_self_plan` 来修。** 那个函数的注释记着两次教训：
放宽后 E03 被误判重答、**编出了一个不存在的余量 2.715mm**；E09 被误判两次、
**丢掉了一份带引用和公式的合格回答**。正确的修法是加一条**独立的高置信度信号**：
「整段文本就是一个工具调用 JSON 块」—— 给医生的最终答案不可能是裸 JSON，这条判据不会误伤。

顺带暴露的第二个问题：**`stop_reason` 不可信**。这条用例最终被记为 `answered`，
但它显然没回答。任何一个只看 `stop_reason` 的上层（网页版、演示脚本）都会被骗。

### 发现 3 · E15 结论与工具输出相反，却没被判失败

E15 在全量跑里失败的那次（`inspect_case → plan_route`，缺 `rank_candidates`）：

```
模型写的：  …该结节适合进行支气管镜导航…
同一段里：  路径可达性：分级为 "marginal"（边缘），表示路径明显偏离气道，需人工复核…
           ↑ 直接把工具的告警文案抄了过来，结论却说「适合」
```

它还传了 **`device_diameter_mm: 0`** —— 外径 0 意味着「任何路都过得去」，结论天然偏乐观。

而这一条**没被任何一个打分器判失败**：`must_include=("复核",)` 靠照抄工具文本就满足了；
`tool_selection` 只查「调了哪些工具」。用例的 rubric 明明写着
「必须提示偏离气道、需人工复核，**不得只报一条路径就说可行**」——
**这条要求没有被做成断言。**

同一类「空心通过」还有一处：**E14P 是靠规划了另一个候选通过的。**
E14 要求「候选越界应当失败并给出可用范围」，但用例没有 `expect_args`，
所以「调了 `plan_route`」即可，拿哪个候选规划都不管 —— 规则基线在改写集上正是这样过的。

## 五、结论与下一步

### 已经成立的三件事

1. **评测重新有了区分度**：同一批意图换个说法，规则基线 15/15 → 3/15，模型 15/15。
   「泛化」这件事第一次有了可复现的数字。
2. **`heuristic.py` 那条不变量被数据推翻，现在有了可复查的证据**
   （不是靠读注释，是靠两份报告）。
3. **同义改写的干净度进了门禁**（`agent/eval/selftest.py` 的 `[3]` 项），
   尺子一致性由 `dataclasses.replace` + `audit()` 结构保证。

### 尚未成立、但已经能说清楚的四件事（按含金量排序）

| # | 事项 | 为什么它更值钱 | 起步证据 |
|---|---|---|---|
| 1 | **工具调用写成正文时没有兜底** | 这是「模型不按协议输出怎么办」，Agent 岗必问；且 E07 是**稳定失败**，修完能直接看到分数动 | E07 0/5，参数其实传对了 |
| 2 | **`stop_reason` 会撒谎**（裸 JSON 交付却记 `answered`） | 上层一切「是否成功」的判断都建立在它上面 | E07 的 trace |
| 3 | **结论与工具字段相反没有判据** | 工具选对了、参数传对了，结论还能反着说 —— 这才是落地时最危险的一类错 | E15 的答案 + `marginal` |
| 4 | **单次评测分数不稳**（E15 ≈ 1/6 偶发；历史 15/15 与今日 13/15 不可比） | 「跑一次就宣布进步」是评测里最常见的自欺 | E07/E15 各 5 次重复 |

### 建议顺序

**1 → 2**（同一处代码，一起改）：给 `_looks_like_intent_to_act` 加「裸工具调用 JSON」这一条独立信号，
顺手把「疑似工具调用被当成答案」记为独立的 `stop_reason`。
验收：E07 从 0/5 回到 5/5，且 E03/E09 那两个历史误判**不复发**（现有 selftest 覆盖）。

**3**：加一个「结论与工具字段一致性」打分器。
验收：工具返回 `marginal`/`unreachable` 而回答出现「适合/可行」→ 判失败；
先用 E15 那条真实失败样例当 fixture（有原文，不必合成）。

**4**：给 `run_eval` 加 `--repeat N`，报告输出每条用例的通过率而不是单次布尔。
验收：报告能给出每个用例的 N 次通过率；改代码前后比的是**通过率**，不是单次结果。

> 这一步之所以排最后，是因为前三步做完以后，分数本身就会动 ——
> 先有稳定的读数，再谈「进步了多少」。
