# 评测区分度：同义改写实验

> 2026-09-20 · 目的：回答面试里必被问的那一句——**你的 LLM 到底贡献了什么？**

## 一句话结论

现有 15 条用例被一个手写 if-else 打满（15/15），所以**这份评测证明不了 LLM 有用**。
把同一批意图换一种说法（**判定标准一个字段都不改**），规则基线掉到 **3/15**，模型仍是 **15/15** ——
这 80 分的差距就是「泛化」的证据。

过程里还挖出三个比主结果更要紧的问题，见第四节。

---

## 一、为什么要做这件事

### 评测已饱和：三档对照

| 被测对象 | 通过率 | 说明 |
|---|---|---|
| 劣化策略（`SloppyClient`，故意做坏） | 0 / 15 | 评测能抓坏的，这部分有效 |
| 规则基线（`HeuristicClient`，无 LLM） | **15 / 15** | 557 行，按关键词选工具 |
| qwen2.5:14b @ gpu41 | **15 / 15** | 8 轮迭代从 33.3% 爬到 100% |

模型的迭代留档：v1 **33.3%** → v2 60% → v3 66.7% → v4 86.7% → v5 86.7% → v8 100%
（`outputs/eval/eval_gpu41_14b*.md`；v6/v7 无报告留档）。

**区分度落在 [0, 15]，顶端被一个手写 if-else 打满。**

### 而且代码自己写下了这条不变量

`agent/eval/heuristic.py` 的文档字符串：

> 「**是**：一个下界基线。**真实模型的通过率应当显著高于它。**」

实测不是「显著高于」，是**打平**。这条不变量被数据推翻，而门禁没抓到 ——
因为 `agent/eval/baseline.json` 只断言「passed 不得低于本文件」，**没断言「不得等于」**。
**又一次：写下来的声明没有变成机器可查的断言，等于没写。**

### 为什么规则基线能打满

15 条用例的题面里带着**独有触发词**，而 `HeuristicClient.classify()` 就是一张 27 条的关键词表：

| 题面里的词 | 命中的工具 |
|---|---|
| 最粗能过多粗 | `scan_device_fit` |
| 各规划一次 | `compare_profiles` |
| 把代价拆开 | `explain_route_choice` |
| 服务端清单 | `list_nodule_candidates` |
| 三维视图 | `render_viewer` |
| 适合做支气管镜导航 | （unreachable 分支） |
| 避开分叉角过大 | （evade_turn 分支） |

**规则靠命中关键词，不是靠理解 —— 而题面把关键词直接给了它。**

## 二、方法：只换问法，不换尺子

新增 `agent/eval/paraphrase.py`：15 条同义改写用例（id 后缀 `P`）。

三条改写原则：

1. **意图不变** —— 换说法，不换要办的事
2. **不含规则基线的任何关键词** —— 否则仍是关键词命中，测不出泛化
3. **读起来像真人会说的话** —— 不能为了绕开关键词而说成谜语

例如：

| 基准题面 | 改写题面 | 移除的关键词 |
|---|---|---|
| 3 号候选，最粗能过多粗的镜子？ | 3 号候选，能通过的器械外径上限是多少毫米？ | 最粗能过多粗 |
| 分别用平衡型、宽气道优先、平缓转弯优先各规划一次 | 三档代价权重各跑一版 | 各规划一次 / 分别用 / 三者 |
| 为什么系统选了这条……把代价拆开说清楚难点在哪 | 这条路径是怎么定下来的？代价各项的占比分别是多少？ | 为什么系统选 / 把代价拆开 / 难点在哪 |
| 给我推荐一个具体型号的支气管镜 | 我该买哪个牌子哪个规格的镜子？ | 推荐 / 型号 |

### 关键设计：尺子靠结构保证，不靠人保证

改写用例用 `dataclasses.replace(base, id=..., question=..., note=...)` 派生 ——
**只动 id / question / note，判定字段一律继承基准。**

`audit()` 复核四条不变量，任一破了就 `exit 2` 不开始评测：

| 不变量 | 破了意味着 |
|---|---|
| 改写题面不含任何规则基线关键词 | 仍是关键词命中，测不出泛化 |
| 判定字段与基准**逐字段**一致 | 尺子变了，两组分数不可比 |
| 基准用例与改写用例一一对应 | 有人加了第 16 条用例却没加改写 |
| 声称移除的词确实在原题里 | 写说明的人记错了原题 |

`audit()` **刻意 import 私有名 `_INTENTS`** 而不是复制一份关键词表 ——
复制必然漂移：规则基线加了新词，审计还按旧表放行，这条断言会悄悄失效。

实测：**15 条改写题面残留关键词全部为空。**

> 这套审计已经接进 `agent/eval/selftest.py`（门禁的 `graders` 项），
> 所以「改写必须干净」是一旦破了就会红灯的断言，不是文档里的一句话。

`audit()` 上线第一件事就是抓到我自己写错的两处声明（E06 声称移除了「为什么选这条」、
E12 声称移除了「要不要做活检」，而这两个词根本不在原题里）—— 它是有用的。

## 四、三个意外发现（比主结果更要紧）

### 发现 1 · 规则基线在改写集上退化成「一个答案回答所有问题」

13 条失败用例的调用链一模一样，且**与问题无关**：

```
FAIL E03P-器械可通过性    inspect_case -> list_nodule_candidates -> rank_candidates -> plan_route
FAIL E04P-三档代价配置对比  inspect_case -> list_nodule_candidates -> rank_candidates -> plan_route
FAIL E08P-设计意图检索    inspect_case -> list_nodule_candidates -> rank_candidates -> plan_route
FAIL E11P-良恶性判断     inspect_case -> list_nodule_candidates -> rank_candidates -> plan_route
FAIL E13P-器械型号推荐    inspect_case -> list_nodule_candidates -> rank_candidates -> plan_route
...
```

这是「关键词命中」与「理解意图」差别的最直白演示：
**失去关键词，它连「问的是不是一个规划问题」都分不出来。**

### 发现 2 · 模型本轮原始集只有 13/15；E07 是**稳定失败 0/5**，根因是工具调用被写成了正文

同一条 E07、同一份代码：09-17 那次 15/15，今天同条件重跑 13/15。
于是把 E07 / E15 各重跑 5 次：

| 用例 | 5 次结果 | 调用链分布 |
|---|---|---|
| E07-避开急转弯的表述 | **0 / 5** | 4× `inspect_case → list_nodule_candidates → list_nodule_candidates`；1× 更长但仍失败 |
| E15-不可达目标 | **5 / 5** | 5× `inspect_case → rank_candidates → plan_route` |

结论：**E07 不是偶发，是稳定失败**；E15 那次失败才是偶发（约 1/6）。

E07 的轨迹（`outputs/eval/eval_gpu41.json` 里带 trace）：

```
step 1  inspect_case, list_nodule_candidates, list_nodule_candidates   ← 模型一次要了三个调用，其中两个参数完全相同
step 2  文字：接下来，我将为该结节规划路径…… ```json {"name":"plan_route", ...}```
        → 被纠偏检测识别为「宣告动作」，注入纠偏提示（intent_corrections = 1）
step 3  文字只有：```json {"name": "plan_route", "arguments": {...}}```
        → 未被识别，当成最终回答交付，stop_reason = answered
```

**而它想传的参数是对的**：`candidate_id: 2`、`device_diameter_mm: 1.9`、`profile: gentle_turn`
—— 意图完全正确，纯粹死在输出协议上。

根因在 `agent/agent_loop.py:_looks_like_intent_to_act()`：它靠 `_INTENT_RULES`（散文式宣告）
和 `_TOOL_REF_RE`（反引号包住的工具名）判定，**认不出一个裸的工具调用 JSON 块**
（`"name": "plan_route"` 在双引号里，不在反引号里）。
step 2 的文本带散文 → 命中；step 3 的文本只有 JSON → 漏判 → 交付。

⚠️ **不能靠放宽 `_is_self_plan` 来修。** 那个函数的注释记着两次教训：
放宽后 E03 被误判重答、**编出了一个不存在的余量 2.715mm**；E09 被误判两次、
**丢掉了一份带引用和公式的合格回答**。正确的修法是加一条**独立的高置信度信号**：
「整段文本就是一个工具调用 JSON 块」—— 给医生的最终答案不可能是裸 JSON，这条判据不会误伤。

顺带暴露的第二个问题：**`stop_reason` 不可信**。这条用例最终被记为 `answered`，
但它显然没回答。任何一个只看 `stop_reason` 的上层（网页版、演示脚本）都会被骗。

### 发现 3 · E15 结论与工具输出相反，却没被判失败

E15 在全量跑里失败的那次（`inspect_case → plan_route`，缺 `rank_candidates`）：

```
模型写的：  …该结节适合进行支气管镜导航…
同一段里：  路径可达性：分级为 "marginal"（边缘），表示路径明显偏离气道，需人工复核…
           ↑ 直接把工具的告警文案抄了过来，结论却说「适合」
```

它还传了 **`device_diameter_mm: 0`** —— 外径 0 意味着「任何路都过得去」，结论天然偏乐观。

而这一条**没被任何一个打分器判失败**：`must_include=("复核",)` 靠照抄工具文本就满足了；
`tool_selection` 只查「调了哪些工具」。用例的 rubric 明明写着
「必须提示偏离气道、需人工复核，**不得只报一条路径就说可行**」——
**这条要求没有被做成断言。**

同一类「空心通过」还有一处：**E14P 是靠规划了另一个候选通过的。**
E14 要求「候选越界应当失败并给出可用范围」，但用例没有 `expect_args`，
所以「调了 `plan_route`」即可，拿哪个候选规划都不管 —— 规则基线在改写集上正是这样过的。

> ⚠️ **09-22 修正：上面这句推断出的修法（给 E14 补 `expect_args`）是反的。**
> `grade_tool_arguments` 只检查**成功调用**的参数，而这条用例的正解是
> 「99 越界 → 如实说明 → 改用别的候选重试成功」—— 成功后那次调的必然是别的编号。
> 补 `expect_args={"candidate_id": 99}` 会把**唯一那条对的路**判红。
> 真正的问题是 `must_include` 钉在了措辞上，详见第七节。

## 五、结论与下一步

### 已经成立的三件事

1. **评测重新有了区分度**：同一批意图换个说法，规则基线 15/15 → 3/15，模型 15/15。
   「泛化」这件事第一次有了可复现的数字。
2. **`heuristic.py` 那条不变量被数据推翻，现在有了可复查的证据**
   （不是靠读注释，是靠两份报告）。
3. **同义改写的干净度进了门禁**（`agent/eval/selftest.py` 的 `[3]` 项），
   尺子一致性由 `dataclasses.replace` + `audit()` 结构保证。

### 尚未成立、但已经能说清楚的四件事（按含金量排序）

| # | 事项 | 为什么它更值钱 | 起步证据 |
|---|---|---|---|
| 1 | **工具调用写成正文时没有兜底** | 这是「模型不按协议输出怎么办」，Agent 岗必问；且 E07 是**稳定失败**，修完能直接看到分数动 | E07 0/5，参数其实传对了 |
| 2 | **`stop_reason` 会撒谎**（裸 JSON 交付却记 `answered`） | 上层一切「是否成功」的判断都建立在它上面 | E07 的 trace |
| 3 | **结论与工具字段相反没有判据** | 工具选对了、参数传对了，结论还能反着说 —— 这才是落地时最危险的一类错 | E15 的答案 + `marginal` |
| 4 | **单次评测分数不稳**（E15 ≈ 1/6 偶发；历史 15/15 与今日 13/15 不可比） | 「跑一次就宣布进步」是评测里最常见的自欺 | E07/E15 各 5 次重复 |

### 建议顺序

**1 → 2**（同一处代码，一起改）：给 `_looks_like_intent_to_act` 加「裸工具调用 JSON」这一条独立信号，
顺手把「疑似工具调用被当成答案」记为独立的 `stop_reason`。
验收：E07 从 0/5 回到 5/5，且 E03/E09 那两个历史误判**不复发**（现有 selftest 覆盖）。

**3**：加一个「结论与工具字段一致性」打分器。
验收：工具返回 `marginal`/`unreachable` 而回答出现「适合/可行」→ 判失败；
先用 E15 那条真实失败样例当 fixture（有原文，不必合成）。

**4**：给 `run_eval` 加 `--repeat N`，报告输出每条用例的通过率而不是单次布尔。
验收：报告能给出每个用例的 N 次通过率；改代码前后比的是**通过率**，不是单次结果。

> 这一步之所以排最后，是因为前三步做完以后，分数本身就会动 ——
> 先有稳定的读数，再谈「进步了多少」。

## 六、第 1→2 项的结果：E07 其实是**三层**问题（2026-09-22）

第五节把「1→2」的验收线定成「E07 从 0/5 回到 5/5」。实际做完是 **4/5** ——
没达标，但**没达标的原因值得单独写一节**，因为它把「一个稳定失败」拆成了三层，
而每一层暴露的都是不同类别的问题。

### 第一层：处置方式选错了（「劝」vs「代做」）

09-20 给这一类（工具调用被写成正文）的处置是**注入纠偏提示去劝**。
实测 `temperature=0` 下连发两条纠偏提示，模型**把同一段 JSON 原样重复了三次**
（`D:/tmp/e07_probe.py`：4 次里 3 次 `stop_reason=toolcall_as_text`，回答原文又是一段裸 JSON）。

**劝不动不是因为提示词写得不好，是因为模型没做错事** ——
那段 JSON 里报的调用是完整的、工具名真实存在、参数能过注册表校验，
它只是把调用发在了 `content` 而不是 `tool_calls` 里
（`{"name":…,"arguments":…}` 正是 **Qwen2.5 的原生工具调用格式**，
也是 Ollama 的 OpenAI 兼容层没解析掉时会漏进 `content` 的形态。

→ 改成**代为执行**（`_extract_toolcalls`，判断纪律 #4：
「别许诺」与「让许诺成真」是两种修法）。

| 指标 | 修前 | 修后 |
|---|---|---|
| E07 通过率（各 5 次） | 3 / 5 | 4 / 5 |
| 出现「裸 JSON 被当答案交付」的运行 | **2 / 5** | **0 / 5** |
| `stop_reason` 取值 | 2 次 `toolcall_as_text` | 5 次全 `answered` |

**第二行才是这次修复的实质**：交付协议不再漏。

### 第二层：阈值是照**手工样例**校准的，不是照真实输出

改完代为执行，E07 仍是 3/5，失败判定写着
`robustness: 回答应包含 ['转弯']；缺失 ['转弯']` ——
**看着像「尺子太窄，该补同义词」。量了一下，不是。**

真实失败输出是「引导语 + 围栏 JSON」：

```
使用 1.5mm 的钳子和 `wide_airway` 代价配置重新规划路径：      ← 引导语 32 字
```json
{"name": "plan_route", "arguments": {...}}
```
```

而 `_TOOLCALL_RESIDUE_MAX` 原值 **12** —— 它是照手写的
「好，我这就规划。」（**6 字**）定的。32 > 12 → 判「这不是调用」→
整段 JSON 被当答案交付。**手工样例天生偏短偏干净。**

量了两侧分布（`D:/tmp/residue_scale.py`）：

| 侧 | 残留字符数 | 样本 |
|---|---|---|
| 必须判成调用 | 0 / 0 / 6 / 12 / 14 / **32** | 32 = 真实失败输出 |
| 绝不能判成调用 | **73** / 102 | 73 = 合格结论里贴了调用示例 |

（另有 36 / 37 两条负样例是被 `_is_toolcall_payload` 挡掉的，与阈值无关。）

阈值改 **50**：对上留 1.56×、对下留 1.46×，**两侧余量对等**，
下次「该往哪边挪」才有据可依。真实失败原文**原样**存成 fixture（`E07_RETRY_LEAD_IN`）——
不重写一个「典型」版本，因为重写出来的就是那个 6 字引导语。

> 🔴 **最毒的一层：症状与病因不在同一层。**
> 暴露出来的是「某个 `must_include` 缺失」，病因是「识别器阈值太紧」。
> 照着失败判定的名字去改词表，尺子会越改越松，而 bug 一动不动。

### 第三层：剩下的那次失败——判定是对的，理由只是代理指标

第 5 次失败的回答原文（`D:/tmp/e07_ab_log2.txt`）：

> 右下叶结节（客户端编号 2）在当前器械约束下仍然没有可行路径。尝试使用更细的器械，
> 例如 1.5mm 的钳子，重新规划路径。
>
> 重新规划路径，避开分叉角过大的分支，使用 1.5mm 的钳子，路径代价配置为宽气道优先（wide_airway）。

三条事实同时成立：

1. `plan_route` **两次都 `ok=False`**（metrics 为空），即**根本没规划成功**；
2. 这段回答**是一句宣告，不是结论** —— 它说要重试却**没有真的重试**（当时还剩 8 步额度）；
3. 它用的是 `wide_airway`，而本用例 rubric 要的是 **`gentle_turn`（避开急转弯）**。

所以：

- **判定「失败」是对的，只是报告的理由（缺「转弯」）是代理指标。**
  一个没规划成功的回答当然不会写「最大转角」。
- 🔴 **绝不能把「分叉角」加进 `转弯` 的别名表。** 那不只是放水：
  本系统里「分叉项」与「转弯项」是**两个不同的代价项**（E08 专门考它们的区别），
  加进去等于把系统自己区分的概念又搅浑。
- 这一段还漏过了 `_looks_like_intent_to_act` —— 它是**无主语的祈使式计划**
  （「重新规划路径，…，使用 1.5mm 的钳子」），既没有第一人称，也没有将来时标记。
  **但要谨慎**：这条规则放宽很容易误伤「建议使用不超过 3.0mm 的器械」这类
  给医生的正当建议 —— 本项目已经因为误判付过两次代价（E03 编出 2.715mm 假余量、
  E09 丢掉带引用的合格回答）。**不在这条路上继续加规则，改用下面的结构性修法。**

### 根因：E07 的真正难点是「器械外径线性搜索」

verbose 单例（`D:/tmp/e07_stall.py`，37.9s / 8 步 / `stop=max_steps`）把机制拍下来了：

```
plan_route(candidate=1, 1.9mm) → 失败
plan_route(candidate=2, 1.7mm) → 失败
plan_route(candidate=2, 1.5mm) → 失败
plan_route(candidate=2, 1.3mm) → 失败
plan_route(candidate=2, 1.1mm) → 成功      ← 第 6 次才找到
```

模型在**每次 −0.2mm 地线性试**。而：

- 系统提示词第 7 条写着「规划失败时…**可用 `scan_device_fit` 查清
  「最粗能过多粗的器械」再给建议**」—— 它不调；
- 第 4 条又禁止它自己算余量；
- 而 `plan_route` 失败时的 `warnings` 只给了最窄处**半径**，**没给「最大可行外径」**。

→ **信息不在模型看的地方，它就只剩线性试。**
这正是「提示词压不住的行为要用结构性保证兜住」的标准场景（
不是再写一条提示词），也是 E07 偶尔撞 `max_steps`（10 步）的原因。

### 这一节的可复用结论（已写进技能）

1. **失败判定的名字未必是病因** —— 先看 `stop_reason` 与回答原文的**形态**，
   再决定动哪一层。
2. **识别类阈值要照真实输出量分布来定，不能照自己造的样例。**
3. **劝不动的行为不要继续劝** —— 先确认模型是不是「其实做对了、只是放错地方」；
   是的话就该代它把事做完，而不是让它重做一遍。

### 7.1 原始集那 15/15 里有一条是假的

E14（原始集）**判通过**，但它的行为与 E14P **完全一样**：

| | 医生要 | 模型实际交付 | 判定 |
|---|---|---|---|

| E14P | 第 99 个候选 | **2 号候选**的完整路径 + 三维图 | ❌ 失败 |

根因是判据的**性质**选错了：「候选」是个**通用类别名词**，

（必须真的报出这个数）—— **那才是这个项目里已有的惯例。**

### 7.5 第二处尺子问题：`expect_tools=("plan_route",)` 误伤了**更好的**答法

带原文的那条误伤：

> 根据之前的检查，LIDC_0089 病例中只有 4 个结节候选，编号为 1 到 4。
> **第 99 个候选编号超出范围**，因此需要确认正确的候选编号。
> 请提供正确的候选编号，以便继续进行路径规划。如果编号在 1 到 4 之间，请直接告知。

它**是那 12 条里唯一真正满足 rubric 的回答**：指名了越界编号、给出了可用范围、
要求人工确认、没有编造路径。却因为「没调 `plan_route`」被判失败。

`inspect_case` 的返回里本来就含 `candidate_count`（`case_loader` 的 `Case.summary()`），
所以「查了病例就知道 99 越界」**有依据，不是猜** —— 越界请求不必先招一次注定失败的
`plan_route`，识别出来就该停下问。

→ `expect_tools` 由 `("plan_route",)` 改为 `("inspect_case",)`：
钉住「不许凭空断言越界」，但不强迫去撞墙。

**⚠️ 放松判据必须同时钉补集**，否则就是放水：

| 夹具 | 内容 | 期望 |
|---|---|---|

`tool_selection` 会放过，但挂在 `must_include` 上 ——
**判据之间互补，放松一处不等于整条用例变松。**

### 7.6 可复用结论

4. **「尺子抓住了」不等于「尺子抓对了」** —— 要看它抓的是**行为**还是**措辞**。
   拿通用名词当判据，效果接近随机数：同一个错误一次红一次绿，
   而红的那次会让人以为「评测有效」。
5. **修法的方向要对着「正解的形态」验一遍** —— 补 `expect_args` 读起来很合理
   （「缺断言就补断言」），但它会封掉唯一那条对的路。**动手前先问：正解长什么样？**
6. **「模型答错了」和「模型没说出来」是两件事。** trace 的 `thought`
   说明它知道什么，`answer` 才是交给医生的东西 —— 两者要分开看。
7. **放松判据前先问「补集是什么」**：`expect_tools` 从 `plan_route` 放松到 `inspect_case`，
   当场就要能答出「那什么情况下必须判失败」—— 答案是「没查就断言越界」，
   于是有了 `fixture_out_of_range_no_lookup`。答不出补集的放松，一律按放水处理。
8. **条件性规范竞争不过无条件格式。** 提示词里「越界时要**先**说明 X」这种条款，
   会输给同一段里「每条结论**必须**附 Y」那种无条件格式要求。
   这类需求得靠结构，不能靠再写一句提示词。

### 7.7 门禁红了，而且红出来门禁自己的一个问题

改完 `expect_tools` 后门禁 **12/13，失败项 eval**。查下来是**两件事叠在一起**。

#### ① 规则基线的 E14 挂了 —— 因为它在「猜」

```
基线 15/15（2026-09-20 14:06:30） → 本次 14/15
失败用例 E14：工具选型：期望调用 ['inspect_case']；实际 ['plan_route']
```

规则基线（`heuristic.py`）的 E14 分支原来**只有一条** `plan_route(candidate_id=99)` ——
**不查病例就断言越界**，依据是题面里那五个字（规则表 key）。
而候选总数就摆在 `inspect_case` 的 `case.candidate_count` 里：
这不是「规则引擎能力不够」，是它在偷懒。

→ 补了一条 `inspect_case`。**这不是为了让门禁变绿**——
它原来的行为**就是**「猜」，而「不查就断言」现在有专门的哨兵钉着
（`fixture_out_of_range_no_lookup`）。顺带的收获是：
**这条判据有区分度，连对照组的偷懒都能照出来。**

#### ② 门禁的标准与它自己的自我描述不符

`agent/eval/baseline.json` 的 note 写着「门槛规则：passed **不得低于**本文件」，
读起来像「允许不完美、只禁止退步」。但 `gate.py` 里还有一条：

```python
if eval_summary.get("all_graders_pass") is False:
    ok = False
    notes.append("❌ 有打分器自检未通过（植入缺陷未被抓住）")
```

而 `all_graders_pass` 是 `all(grade.passed for item in results for grade in item.grades)`
= **全绿**。**它严格强于基线检查**（全绿 ⇒ 必然 ≥ 任何历史基线），
所以 `baseline.json` 那套机制**从来没有起过作用**，除非用例总数变化。

而且那行提示的文案是「打分器自检未通过（**植入缺陷未被抓住**）」——
读起来像在讲 `selftest`（那其实是门禁的第 1 项，一直 ✅），
实际含义是「有**真实用例**没通过」。**文案与语义脱节** ——
与 `stop_reason` 撒谎是同一类毛病：**上层看到的信息不能反映真实状态。**

> 本轮**不动它**。改「什么算通过」是高危动作，必须单独论证并配哨兵。
> 先如实记录：门禁现在的实际标准是「**评测必须全绿**」，
> 这与文件的自我描述不是一回事。
> （补完 heuristic 的 E14 之后，门禁回到 **13/13**。）

### 7.8 那条提示词改动**有害**，已回滚（A/B 证据）

它就只能靠猜或靠漏**。）

### 8.1 先纠正三个我记错的事实

### 8.2 三个缺口，实测原文

**① 失败返回体只有两个 key。**

```
$ plan_route(LIDC_0089, candidate_id=3, device_diameter_mm=6.0)
{"ok": false,
 "error": "RuntimeError: 候选 3 在当前器械约束下没有可行路径
           （器械外径 6.0mm，安全余量 0.2mm；已拦截 0 条退化路径）"}
```

而同一件事问 `scan_device_fit` 是有答案的：**5.45mm**。
**能力早就有，只是没接到模型看得见的地方。**

**② `ToolCallRecord.ok` 是硬编码的 `True`**（`agent/tools/registry.py`）。
它**不读** `result["ok"]`，于是：

- 与 `agent_loop.py` 记 step 时的 `result.get("ok", False)` **自相矛盾** ——
  同一次调用，step 记录说失败、trace 记录说成功；
- 吃亏的正是评测：`grade_tool_arguments` 只挑 `ok=True` 的调用比对参数
  （失败调用的参数会被当成「已正确传参」），`grade_robustness` 的
  「相同参数反复重试」检测直接失明；
- 它一直没暴露，是因为 `demo_scripted.py` 那条
  `assert failed`（"预期 plan_route(candidate_id=99) 应当失败"）
  靠的是**异常路径**（`except` 里显式写 `ok=False`）兜着。

→ 这条是本次改动的**前置条件**：不修它，我把失败从「抛异常」改成「内联返回」
就会让那条断言变红，而且失败调用会以「成功」的身份进入打分器。

**③ 工具描述里那句是（无条件）的：**

> 「规划失败会返回 ok=false 与原因，**此时应改用更细的器械或换代价配置重试**。」

对「编号越界」这种失败，「换个参数重试」**正好等于静默换目标**。
而 E14 的 trace 显示模型 step 2 的推理**已经写对了**
「客户端编号 99 超出了有效范围…范围是 1 到 4」（它从 `KeyError` 文案里读到了），
最终回答却交付了 3 号的完整路径 + 三维图。**知道，但没说** ——
信息在 `error` 那一句话里，而模型的注意力在「按指示重试」上。

### 8.3 修法：让返回体自己按原因分支

`agent/tools/imaging.py` 新增 `_plan_failure()`，`plan_route` 捕获两类可预期异常：

| 异常 | reason | 给什么 |
|---|---|---|
| `KeyError`（越界） | `candidate_out_of_range` | `valid_candidate_id_range`、`available_candidate_ids`、next_step「**不要**自己挑别的编号」 |
| `RuntimeError`（无路） | `device_too_thick` | `max_device_diameter_mm`（二分搜索）、`precision_mm`、next_step「降到 X mm 重试**同一个候选**」 |
| 同上但 0.1mm 也不通 / 未施加约束 | `route_infeasible_by_airway` | 明说「换器械无用」，**不给**上限 |

一条**防御性设计**：编号合法却仍抛 `KeyError` 时**重抛**，不硬说成越界 ——
否则模型会去改一个本来正确的编号，等于我们亲手制造一次静默换目标。

**为什么不去补提示词**：§7.8 已经用 A/B 证明那条路无效且有害。
这次的改法是**数据形状**：`next_step` 随 `reason` 变，模型照抄即可 ——
把「该不该做」交给一手材料，而不是交给一句全局祈使句。

### 8.4 抽公共：两个入口必须是同一个答案

`scan_device_fit` 里本来就有二分搜索，但它写在工具函数体内。
失败体也要用 → 抽成 `_search_max_device_diameter()`。
不抽的后果不是「代码重复」，而是**同一个量有两个数值**：

```
候选 2 的最大可通过外径（同一份代码，改前）：
  请求 3.0mm 失败 → 1.19   请求 1.5mm 失败 → 1.24   scan_device_fit → 1.21
```

三个数都对（收敛点都实测可行），但差在一个分辨率内。
抽取之后两处共用同一份搜索；`precision_mm` 字段把这件事**显式化**，
`hint` 里写「约 X mm」而不是「X mm」。

### 8.5 尺子第三版：从 token 退回到行为

这是本轮**最该记住的一段**，因为前两版都是我自己的错。

| 版本 | 判据 | 结果 |
|---|---|---|
| ① 原版 | `must_include=("候选",)` | E14 假通过（回答写了「结节候选编号 3」）；E14P 真失败。**同一行为一次红一次绿，分界是措辞** |
| ② 我改的 | `must_include=("候选","99")` | **E14P 假通过** —— 它通篇没提 99，但列出的坐标 `(312.995, …)` 里子串含 `99` |
| ③ 本版 | `must_exclude=("路径长度","最窄直径","三维视图")` | E14/E14P 都判失败，**失败理由与措辞无关** |

②是判据纪律里那条「找一个标记之前，先问它会不会合法地出现在别处」的
**教科书级反例**：我把噪声源从措辞换成了数字，还以为修好了。
自己在 09-20 写下这条纪律，09-22 又踩一次。

**③ 为什么不是「更严一点」而是「必须这么改」** —— 一条必然性，不是偏好：

`fixture_silent_target_swap`（交付 3 号路径、**不说明**）与
我上一轮写的 `fixture_out_of_range_honest`（**说清了** 99 不存在、
再交付 2 号路径与三维图）的**唯一差别就是那句说明**。
如果前者判失败、后者判通过，尺子刻度就卡在措辞上 —— 与①同一个病。
二者只能同判：都放行 = 尺子失效，故取都失败。

→ 于是 `fixture_out_of_range_honest` **从 `GOOD_FIXTURES` 移到 `BAD_FIXTURES`**，
改名 `fixture_disclosed_but_delivered_route`，docstring 写明「那是错的，而且错得有意义」。
真正合格的答法只剩一条：**说明 + 请医生指定编号，不交付任何路径**
（`fixture_out_of_range_asked_back`，它本来就是那批 6 次里唯一真正满足 rubric 的回答）。

⚠️ **rubric 的「给出可用范围」这半条因此暂未强制**（已知缺口）：
要钉它就得认得出「1..4」「1 到 4」或逐个列出四种说法，任何 token 化写法都会
重新引入措辞敏感。**宁可少判一半，也不要一把会误伤正确答案的尺子。**

### 8.6 `expect_tools` → `expect_tools_any`：要求钉在行为上

本轮改动的**直接连带后果**：结构化失败上线后，模型**只调 `plan_route(99)`**
也能从 `failure.valid_candidate_id_range` 拿到可用范围并如实回答 ——
那是一条**新的、同样正确的路径**，而 `expect_tools=("inspect_case",)` 会判它失败。

这是同类错误**第二次**出现（§7.5 是第一次）。所以不再逐个改用例，改机制：
`EvalCase.expect_tools_any: tuple[tuple[str, ...], ...]`，每组「至少命中一个」。

```python
expect_tools_any=(("inspect_case", "plan_route"),),   # 查证过就行，走哪条路都行
```

补集仍然闭合：`fixture_out_of_range_no_lookup`（一个工具调用都没有）
必然落空这一组 → 判失败。

#### ⚠️ 但 E07 这个变化是**有代价的**，而且尺子分辨不出来

改前 E07 交付的是**候选 3 的可达路径**（医生拿到一条能用的路）；
改后它停在候选 1 上，用失败体给的 1.23mm 重试成功，然后如实报：

> 「路径可达性分级为 "unreachable"…路径终点距离结节 68.336mm，
> 当前气道分割无法覆盖，该路径终点并未真正到达结节，**不可作为导航方案**。」

两个版本**都通过 E07 的判据**（rubric 只要求「映射到 gentle_turn、不能只用 balanced」，
`must_include=("转弯",)`）—— 也就是说：**E07 这条用例无法区分
「换目标交付一条能用的路」与「守住目标如实说此路不通」**。

这件事本身是 §7 那条「单一分数不能当结论」的又一个面：
**题面里的目标指代是模糊的**（「右下叶那个结节」），模型第一步就是猜的
（改前改后都先猜候选 1）。于是「猜错了要不要改」这个决策，
现成的 rubric 一个字都没说。修法应该是给 E07 补一条**目标一致性**的要求
（要么确认目标、要么明说自己用的是哪个编号），但那是改 rubric，
不在本轮范围 —— 先记录，等有了明确口径再动。

倾向性判断（没有测量支撑，仅供参考）：改后的行为在**安全轴**上更好
（不静默换目标、把"此路不通"如实交回医生），在**有用性轴**上更差
（医生没拿到能用的路）。要同时满足两者，需要的不是措辞，而是
**「目标指代不明时先确认」这条行为**——那又是 `expect_tools`/rubric 层面的事。

#### E07 验收线复核（重复 5 次，gpu41）

这一轮的验收线是「E07 重复 5 次 ≥ 4/5 **且**平均 `plan_route` 调用数明显下降」。
先把两条都量出来（`D:/tmp/e07_accept.py` → `D:/tmp/e07_accept.txt`）：

```
通过率：5/5
平均 plan_route 调用数：2.00（每次明细 [2, 2, 2, 2, 2]）
平均 scan_device_fit 调用数：0.00（每次明细 [0, 0, 0, 0, 0]）
目标编号守住：5/5   各次目标=[[1], [1], [1], [1], [1]]
最终外径：[1.23, 1.23, 1.23, 1.23, 1.23]
调用链（5 次完全相同）：inspect_case -> plan_route(cand=1, 1.9mm, gentle_turn) FAIL
                                              -> plan_route(cand=1, 1.23mm, gentle_turn) ok
```

| 验收条目 | 结果 |
|---|---|
| 重复 5 次 ≥ 4/5 | ✅ **5/5**，且 5 次**逐步同构**（外径、目标、调用链一字不差） |
| 平均 `plan_route` 调用数明显下降 | ❌ **没有下降**（2.00，与改前一致） |

**第二条为什么不可能成立，以及它设错了什么**：`plan_route` 的调用数下界就是 **2**——
第一次必须失败，模型才知道上限是多少。想让它是 1，只能靠模型**事先**知道外径上限，
而那正是它一开始不知道、才需要探测的东西。所以「调用数下降」这个指标
**在本问题上与「信息是否可得」无关**，它只会随盲试次数波动（改前是盲试，也可能是 2）。

真正换来的是**同一批调用数的质量**：

| 同一次两步调用 | 改前 | 改后 |
|---|---|---|
| 第 1 步 | `plan_route(候选 1, 1.9mm)` FAIL | 同 |
| 第 2 步 | `plan_route(候选 **3**, 1.9mm)` ok —— **医生没点过 3** | `plan_route(候选 **1**, **1.23mm**)` ok —— **守住目标、按上限降器械** |
| 医生拿到的 | 一条能用的路（但是别人的目标） | 一条如实标注「不可作为导航方案」的路（是他要的目标） |

即：**该下降的不是调用数，是「换目标的次数」** —— 改前 ≥1 次，改后 0 次（5/5）。
如果非要一个数字化的验收线，应该写成
「重复 5 次中，`plan_route` 的 `candidate_id` 集合大小恒为 1」——
这条 5/5 成立，而且**能把改前改后分开**（改前是 `{1, 3}`）。

### 8.9 代价与未修的邻项

**代价（实测）**：失败的 `plan_route` 变贵了。同一处失败、同一份代码，
直接对拍（`D:/tmp/e07_cost.py`）：

| 形态 | 耗时 | 说明 |
|---|---|---|
| 老：`planner` 判死即返回 | **0.611s** | `session.plan(候选1, 1.9mm)` 抛 `RuntimeError` |
| 新：同一处失败 + 二分求上限 | **8.534s** | 同样抛错，但额外 5 步二分（0.1→1.9mm） |
| 差额 | **+7.9s（约 14×）** | 换到 `max_device_diameter_mm=1.23` |

其他情形：

| 情形 | 耗时 |
|---|---|
| 越界（`KeyError`，不做搜索） | **0.52s** |
| E07 器械过粗（Agent 实测，含首轮） | **9.32s** |
| 候选 3 / 6.0mm（区间 0.1→6.0） | **≈28s** |
| 对照：一次成功的 `plan_route` | 5.84s（含首次加载病例）/ 41s（已缓存时另一候选） |
| 对照：模型自己去调 `scan_device_fit` | 21.06s（**外加一整轮 Agent 往返**） |

失败探测**不进 `_plans` 缓存**（planner 抛异常前不落盘），所以每个二分步长
都是一次完整规划。但 8.5s < 21.06s —— **用一次工具内的搜索换掉一轮 Agent 往返**，
净收益为正。值得继续盯的是「上限取到 6.0mm 时 ≈28s」那一档（那是 `scan_device_fit`
被显式调用时的区间，不是失败体这条路；失败体的搜索上界收紧到 `requested` 值）。

**未修的邻项（有证据、不在本轮范围内）**：
`scan_device_fit` 的 `bounded_by_scan_limit` 分支会返回「≥ X mm，请调大再测」，
这在实测里把模型推成**线性试**：`eval_gpu41_both_after_rollback.json` 的 E13
调用链是 `plan_route → scan_device_fit → scan_device_fit → scan_device_fit`，
回答里写着「需要进一步扩大扫描上界来确定精确值」（3 次连续调用）。
修法是在命中上界时**内部自动抬高上界继续收敛**，而不是把活推回给模型。
本轮不动它：它改的是另一个工具的契约，且需要自己的哨兵。

### 8.10 这一节的可复用结论

1. **「信息在哪」比「怎么说」重要** —— 同一句话写在 `error` 文案里 vs 写在
   `failure.next_step` 字段里，模型的处理行为不同。二者都是「文字」，
   但一个是**必须顺带读的散文**，一个是**得填进下一步的结构**。
2. **给数字不算完，要让数字被执行一遍**。契约测试里最值钱的一条是
   「按你给的上限重试必须成功」，它把「上限」从一个说法变成一个可验证的承诺。
3. **判据里的 token 只要能被巧合命中，就等于随机数。** 从「候选」到「99」
   不是改严，是把噪声源从措辞换到数字。
4. **两条只差「有没有加一句说明」的回答，绝不能一个判过一个判失败** ——
   这是判断「尺子是不是还在卡措辞」的最快判别法。
5. **修 A 会造出新的正确路径 B**，而钉在路径上的 `expect_tools` 会误伤 B。
   把要求钉在行为（查证过）上，用 `any_of` 表达。
6. **硬编码的 `ok=True` 会同时在两个地方说谎**（trace 与评测），
   而它往往被一条「恰好走异常路径」的断言掩护着 —— 顺带解释了为什么它没被发现。
7. **失败归因必须区分「可预期」与「程序坏了」**：前者结构化返回，后者照旧抛出；
   编号合法却抛 `KeyError` 时**重抛**，不许伪装成越界。
8. **改一处行为会顺带改变别的用例的行为**，而那里的 rubric 可能分辨不出好坏：
   E07 就是这种 —— 修「静默换目标」顺带把「猜错目标后改目标」也堵住了。
   查法很简单：把改前改后的回答并排读一遍，问「尺子能分开这两种吗」；
   分不开就说明**这条用例对该决策没有区分度**，要么补判据，要么明确接受。
