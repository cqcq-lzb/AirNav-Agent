# AirNav-Agent 企业级差距清单

> 盘点时间：2026-09-20
> 判据：能否被**信任**（安全与合规）、能否被**运维**（服务化与可观测）、能否被**使用**（临床价值）。
> 相关文档：`docs/P0改造方案_鉴权与审计日志.md`、`outputs/gate/gate_report.md`（门禁现状）

---

## 一、结论先说

Agent 内核（ReAct 循环、11 工具、评测与反幻觉、几何优化）已经**超过绝大多数 demo 项目**。
企业级的差距不在「功能数量」，全部集中在**服务与治理层**——也就是下面 P0/P1 两个分级里。

一句话：**这套系统的智力是够的，缺的是「可运营性」。**

## 三、差距清单

### P0 · 合规底座（先做，1.5~2 天）—— ✅ 已完成（2026-09-20）

> 详见 `docs/P0改造方案_鉴权与审计日志.md`（含实现记录与自检抓出的两个真 bug）

| 项 | 现状 | 缺口 | 验收标准 | 状态 |
|---|---|---|---|---|
| 网页端鉴权 | ✅ 已实现：`agent/web/auth.py` 纯 ASGI 中间件 + `/login` + HttpOnly Cookie | —— | 无凭据 → 401；`/health` 仍 200；未设 token 时行为不变 | ✅ 27 项鉴权用例全绿 |
| 审计日志 | ✅ 已实现：JSONL + 哈希链（`agent/audit/store.py`），含工具链与产物 sha256 | —— | 每次运行一条记录；改一行必被检出 | ✅ 35 项自检全绿（含四种篡改） |
| 病例数据脱敏（PHI 守卫） | ✅ 已实现：`agent/scripts/scan_phi.py` 扫 NIfTI 文本槽 / JSON / CSV / zip，含自证与清除路径 | —— | 数据面不含患者可识别信息，且这条结论**能失败、进了门禁** | ✅ 9 项自证全绿，真扫 0 命中 |

> **⚠️ 修正记录（2026-09-20）：这条原本写的是「上传前自动清除 DICOM 标签」，侦察后发现无处置放。**
>
> | 原本的假设 | 实测 |
> |---|---|
> | 系统里会流进 DICOM | `find cases -iname '*.dcm'` → **0 个** |
> | 上传口接收 DICOM | `backend/api_server.py:35` → **只接受 `.nii` / `.nii.gz`**，DICOM 从未进入本系统 |
> | 需要「清 DICOM 标签」这个动作 | **没有任何调用方** —— 写出来也没有人能用 |
>
> 更关键的是：**本系统的数据面本来就不含 PHI**（NIfTI 的 4 个自由文本槽
> `descrip`/`aux_file`/`intent_name`/`db_name` **全是空的**）。所以正确的做法不是写一个
> 用不上的清理工具，而是把「我们不持有患者信息」变成一条**能失败、能进回归门禁的断言** ——
> 将来谁往 `cases/` 里丢进带患者姓名的数据，门禁当场拦住。
> 这也解释了为什么该行结论要写成「守卫」而不是「清理」：**清理是一次性的，守卫是持续的。**

### P1 · 服务化与可运维（2~4 周）

| 项 | 现状 | 缺口 | 改造点 | 验收标准 |
|---|---|---|---|---|
| 任务队列与状态机 | `backend/api_server.py` 里 SSH **同步**跑在请求内，断线即失败 | 无队列、无重试、无断点续跑 | 抽 worker 进程 + 状态机（queued→running→succeeded/failed）+ 退避重试 | 杀掉 worker 后重启能续跑；失败可重试且审计留痕 |
| 容器化与离线部署 | `docker/` 只有 `airway-navigation-v3:3.2` 镜像 | Agent + Web 未打包，无离线安装 | 补 Dockerfile + compose，做「无外网一键部署」脚本 | 断网机器上 30 分钟内装好并跑通一次问答 |
| 可观测性 | 只有 SSE 事件与控制台输出 | 无结构化日志、无指标、无 trace | 结构化 JSON 日志 + trace_id 串「一次提问 → 每步工具 → 产物」+ `/metrics` | 一次提问能按 trace_id 捞出全链路；能看到工具耗时分布与失败率 |
| 降级与健康检查 | 有 `heuristic` 规则基线后端（天然是降级路径），但没人用 | 无自动探活与切换 | LLM 探活失败自动降级到规则基线，并在界面标注「当前为降级模式」 | 拔掉 gpu41 网络后提问仍能返回（附降级标识） |
| 依赖与凭据治理 | 有 `scan_creds.py`（手动跑） | 未接 pre-commit，无 CVE 扫描 | `scan_creds.py` 进 hook + `pip-audit` 定期跑 | 提交含疑似凭据必被拦；CVE 报告有处理记录 |

### P2 · 临床能力（持续，按价值排序）

| 项 | 为什么优先 | 改造点 | 验收标准 |
|---|---|---|---|
| **报告导出** | 唯一能交到医生手里的交付物 | 结构化 JSON + Word/PDF（含三维截图、路径参数、器械口径、模型版本） | 一次规划导出一份带图报告，参数与页面所见一致 |
| 病例库管理 | 现在靠扫描目录，无法检索 | SQLite + 元数据（结节数、来源、日期）+ 标签检索 | 按结节数/日期/来源检索到病例，秒级返回 |
| 多轮会话与记忆 | 现在近似单轮，改口径要重说 | 会话历史 + 病例级记忆（已用参数、已否决方案） | 同一会话内改器械外径无需重复病例与候选 |
| 人机协同闭环 | 现在图是「只读终点」 | viewer 内点选目标/标注 → 回灌给 Agent 重规划 | 页面点选结节后 Agent 自动接续规划 |
| 双人核对 | 医疗场景的质量控制要求 | 规划结论「待确认/已确认」状态 + 确认人落审计 | 未确认的结论不能导出报告 |
| 多模态输入打通 | 上传 CT 与 Agent 规划现在两条线 | 后端 job 成功后自动接续 Agent 规划 | 上传 → 分割 → 自动给候选与路径，全程可在页面看到 |

## 四、维护体系（怎么长期不烂）

| 维度 | 做法 | 现状 |
|---|---|---|
| **回归门禁** | `python -m agent.scripts.gate` 一条命令跑完 10 套自检 + 评测基线；数值类（几何、规划）为**硬门禁**；评测分数不得低于 `agent/eval/baseline.json` | ✅ 本次已建立 |
| **审计留痕** | 每次运行一条 JSONL（谁 / 何时 / 哪个病例 / 什么参数 / 哪次工具调用 / 产物指纹 / 模型版本），哈希链防篡改；`audit_verify` 可进 CI，`audit_query` 可导出给人看 | ✅ 本次已建立 |
| **PHI 守卫** | `scan_phi` 扫数据面（NIfTI 文本槽 / JSON / CSV / zip），**自证会叫**（植入 PHI 必命中、已知误报形态必不命中），进回归门禁 —— 把「我们不持有患者信息」从口头承诺变成能失败的断言 | ✅ 本次已建立 |
| **依赖与凭据扫描** | `scan_creds.py` 扫暂存区里的凭据与 DLP 密文 | ✅ 已有（手动跑，未接 hook） |
| **CI** | `.github/workflows/ci.yml` 跑 `--profile ci`（不依赖病例数据的子集） | ⚠️ 仓库无 remote，尚未真正触发；且 `cases/` 不入库 → CI 跑不了全量，需脱敏 fixture（待办） |
| 依赖维护 | 锁文件定期更新 + `pip-audit`；`requirements_mcp.txt` 由 `lock_mcp_deps.py` 可再生 | 手动，待接 hook |
| 凭据扫描 | `scan_creds.py` 接 pre-commit | 手动 |
| 数据与产物生命周期 | `cases/` 只增不减（已 1.9GB）→ 归档策略 + 元数据落库；viewer 产物按病例归档 | 缺 |
| 文档三件套 | 使用指南（有）、部署手册（`deploy/README.md` 待扩写）、**故障排查 runbook**（缺） | 部分 |
| 变更记录 | CHANGELOG + 发布检查清单 + 回滚方案 | 缺 |
| 运行维护 | 日志轮转、磁盘水位告警、gpu41 ollama 探活与自动重启 | 缺（起停脚本已有，加探活即可） |
| 模型版本管理 | nnU-Net 权重版本化 + 指纹，写进审计 | 缺 |

**关于 runbook 的一句判断**：这个项目踩过的坑（DLP 改写依赖文件、user-site 劫持、ollama Vulkan 铺满 8 卡、
`localhost:11434` 被 Remote-SSH 转发、`nohup` 起的服务随调用被杀、改完代码常驻进程不生效……）本身
就是资产。**每个坑一条排查条目**，这份 runbook 的含金量高于任何架构图。

## 五、明确不做（避免过度工程）

| 不做 | 理由 |
|---|---|
| Kubernetes | 单机 + 一台 gpu41 的体量，compose + 进程守护足够；带来的是运维成本不是可靠性 |
| LangChain / LangGraph | 手写循环是当前项目的差异化，且引入后调试链路变黑盒 |
| 微服务拆分 | 拆了就要处理分布式事务与网络故障，收益为负 |
| 自建向量数据库 | 当前知识库规模用 BM25F 就够；向量检索留扩展点（`AIRNAV_EMBED_MODEL`） |
| 多租户 SaaS 化 | 目标是院内私有化部署，不是公有云产品 |
