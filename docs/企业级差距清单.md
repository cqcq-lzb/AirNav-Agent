## 一、结论先说

Agent 内核（ReAct 循环、11 工具、评测与反幻觉、几何优化）已经**超过绝大多数 demo 项目**。
企业级的差距不在「功能数量」，全部集中在**服务与治理层**——也就是下面 P0/P1 两个分级里。

一句话：**这套系统的智力是够的，缺的是「可运营性」。**

## 三、差距清单

### P0 · 合规底座（先做，1.5~2 天）—— ✅ 已完成（2026-09-20）

> 详见 `docs/P0改造方案_鉴权与审计日志.md`（含实现记录与自检抓出的两个真 bug）

| 项 | 现状 | 缺口 | 验收标准 | 状态 |
|---|---|---|---|---|
| 网页端鉴权 | ✅ 已实现：`agent/web/auth.py` 纯 ASGI 中间件 + `/login` + HttpOnly Cookie | —— | 无凭据 → 401；`/health` 仍 200；未设 token 时行为不变 | ✅ 27 项鉴权用例全绿 |
| 审计日志 | ✅ 已实现：JSONL + 哈希链（`agent/audit/store.py`），含工具链与产物 sha256 | —— | 每次运行一条记录；改一行必被检出 | ✅ 35 项自检全绿（含四种篡改） |
| 病例数据脱敏（PHI 守卫） | ✅ 已实现：`agent/scripts/scan_phi.py` 扫 NIfTI 文本槽 / JSON / CSV / zip，含自证与清除路径 | —— | 数据面不含患者可识别信息，且这条结论**能失败、进了门禁** | ✅ 13 项自证全绿，真扫 0 命中 |

> **⚠️ 修正记录（2026-09-20）：这条原本写的是「上传前自动清除 DICOM 标签」，侦察后发现无处置放。**
>
> | 原本的假设 | 实测 |
> |---|---|
> | 系统里会流进 DICOM | `find cases -iname '*.dcm'` → **0 个** |
> | 上传口接收 DICOM | `backend/api_server.py:35` → **只接受 `.nii` / `.nii.gz`**，DICOM 从未进入本系统 |
> | 需要「清 DICOM 标签」这个动作 | **没有任何调用方** —— 写出来也没有人能用 |
>
> 更关键的是：**本系统的数据面本来就不含 PHI**（NIfTI 的 4 个自由文本槽
> `descrip`/`aux_file`/`intent_name`/`db_name` **全是空的**）。所以正确的做法不是写一个
> 用不上的清理工具，而是把「我们不持有患者信息」变成一条**能失败、能进回归门禁的断言** ——
> 将来谁往 `cases/` 里丢进带患者姓名的数据，门禁当场拦住。
> 这也解释了为什么该行结论要写成「守卫」而不是「清理」：**清理是一次性的，守卫是持续的。**

### P1 · 服务化与可运维（2~4 周）

| 项 | 现状 | 缺口 | 改造点 | 验收标准 |
|---|---|---|---|---|
| 任务队列与状态机 | `backend/api_server.py` 里 SSH **同步**跑在请求内，断线即失败 | 无队列、无重试、无断点续跑 | 抽 worker 进程 + 状态机（queued→running→succeeded/failed）+ 退避重试 | 杀掉 worker 后重启能续跑；失败可重试且审计留痕 |
| 容器化与离线部署 | `docker/` 只有 `airway-navigation-v3:3.2` 镜像 | Agent + Web 未打包，无离线安装 | 补 Dockerfile + compose，做「无外网一键部署」脚本 | 断网机器上 30 分钟内装好并跑通一次问答 |
| 可观测性 | 只有 SSE 事件与控制台输出 | 无结构化日志、无指标、无 trace | 结构化 JSON 日志 + trace_id 串「一次提问 → 每步工具 → 产物」+ `/metrics` | 一次提问能按 trace_id 捞出全链路；能看到工具耗时分布与失败率 |
| 降级与健康检查 | ✅ **已完成（2026-09-30）**：`probe_backend` 探活 + 结构化降级标识（CLI 横幅 / `--json` / `/api/meta` / SSE 首事件 / 审计留痕）；`/health` 刻意不接后端（存活 ≠ 就绪，接上会让编排层把「模型不可用」误判成「服务已死」） | — | 探活失败自动降级到规则基线，并在界面标注「当前为降级模式」 | 拔掉 gpu41 网络后提问仍能返回（附降级标识）✅ |
| 依赖与凭据治理 | 有 `scan_creds.py`，且已进 15 项门禁、**CI 每次 push 都跑** | 未接 pre-commit，无 CVE 扫描 | `scan_creds.py` 进 hook + `pip-audit` 定期跑 | 提交含疑似凭据必被拦；CVE 报告有处理记录 |

### P2 · 临床能力（持续，按价值排序）

> ✅ **P2 已交付两项 —— 两者读者不同，不要混。**
> ① **运行与合规报告**（`agent/scripts/report.py`）：面向**审计与合规审查**
> （谁用过、链是否完整、有没有越权、PHI 结论、评测有没有退步），读者是**评审方与运维**。
> ② **临床规划报告**（`agent/scripts/clinical_report.py`）：面向**医生**（器械通过性、
> 靶点可达性、分割依赖复核、路径示意图与内嵌三维视图、器械与模型版本），
> 读者是**要动手的那位**。
> 二者共用同一套地基（单文件 HTML + 打印样式 + 三态结论 —— 三态常量与总判定规则
> **在代码里就是同一个对象**，自检会断言这一点），但内容与判定项完全不同。

| 项 | 为什么优先 | 改造点 | 验收标准 |
|---|---|---|---|

## 五、明确不做（避免过度工程）

| 不做 | 理由 |
|---|---|
| Kubernetes | 单机 + 一台 gpu41 的体量，compose + 进程守护足够；带来的是运维成本不是可靠性 |
| LangChain / LangGraph | 手写循环是当前项目的差异化，且引入后调试链路变黑盒 |
| 微服务拆分 | 拆了就要处理分布式事务与网络故障，收益为负 |
| 自建向量数据库 | 当前知识库规模用 BM25F 就够；向量检索留扩展点（`AIRNAV_EMBED_MODEL`） |
| 多租户 SaaS 化 | 目标是院内私有化部署，不是公有云产品 |

## 七、复核记录

### 2026-09-30

**结论：P1 五项里两项动了，而 CI 从「从未触发过」变成「每次 push 自动跑且绿」。**

| 动作 | 之前 | 现在 |
|---|---|---|
| CI | 「从未触发过」（09-22、09-28 记过两次） | 远端 `cqcq-lzb/AirNav-Agent`（私有）；绿色运行 run **36680366917**，**7m20s**，结论 **14 通过 / 0 失败 / 1 不足以判定** |
| 降级与健康检查 | 「无自动探活与切换」 | ✅ **已完成**：`probe_backend` 探活 + **结构化**降级标识（CLI 横幅 / `--json` / `/api/meta` / SSE 首事件 / 审计留痕）；`/health` 刻意**不接**后端 |
| 依赖与凭据治理 | 「`scan_creds.py`（手动跑）」 | `scan_creds` 已是 15 项门禁的一项，**CI 每次 push 都跑**；pre-commit hook 与 `pip-audit` 仍然缺 |

**CI 第一次真跑连红两轮，红得有价值** —— 暴露的都是「workflow 从没跑过 ⇒ 从没被验证」：

1. `setup-python` 的 `cache: pip` 只认 `**/requirements.txt` 与 `**/pyproject.toml` 两个固定名字，
   仓库里却叫 `requirements_windows.txt` → **11 秒**就报错退出；
2. 手写的安装清单只有 5 个包，实测 `agent/` 还缺 pydantic / pydicom / scikit-image /
   mcp / packaging / requests，且 `navbridge` 在**模块级**拉起 V1 内核（要 vtk + PySide6）；
3. 最值钱的一条：`check_backend` **自己**写死了 `NavSession(root='cases')` 与病例号
   `LIDC_0089` → 在**有真实病例的本机绿、在干净副本上必然红**。这与 09-22 记下的
   `verify_geometry` 是**同一类错**（绕过环境变量读真实数据），属于**第三次复发**。
   已改为走 `case_loader.cases_root()` 的三档解析 + 病例号从 `list_cases` 动态取，
   并把**实际用到的病例来源打进结果**（来历可查）。

⚠️ 上面第 3 条值得单独想办法：**同一类错出现三次，「记得复查」显然不管用**。
下一步应考虑照「内网地址」的先例把它做成**会叫的检查**（扫 `agent/scripts/` 里
写死的病例路径 / 病例号），而不是继续依赖人工复查。

**新增的第 7 类打分器 `id_binding`，起因是一条真实假通过**（不是设计出来的加固）：

`eval_gpu41_both_after_rollback.json` 里 E02P 的模型回答写「界面上显示的编号是 **1** 号」，
而实测真值是 **2** 号（`LIDC_0089` 服务端 1 号 → 客户端 2 号），**它当时判 PASS**。

根因不是「判据太松」，而是**根本没有这条判据**：E02 的 rubric 写了「必须同时出现两种编号」，
但代码里只校验了体素量。而编号是 1~6 的小整数，`grounding` 的行文数字白名单本来就放过 0~12 ——
于是「说对了」与「说错了」在旧判据下**完全同分**（探针：两份回答只差一个数字，4 个打分项全 PASS）。

> **这条的教训比机器值钱：「数字有出处」不等于「数字用对了地方」。**
> 反幻觉做到底，不只是问「这个数是不是编的」，还要问「这个数被安在了对的位置上吗」。

同时被这条判据照出来的：`_EXPECT_FIELDS`（同义改写的「尺子一致性」审计字段清单）
原先没有这两项 —— 漏掉就等于**改写用例可以偷偷放宽编号判据**，而那正是实验最容易被污染的地方。
