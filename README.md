# AirNav-Agent

把一套虚拟支气管镜导航工作站（原为 PySide6 + VTK 的本地 GUI）重构成 **Agent 形态**：
一个手写的 ReAct 循环 + 11 个领域工具 —— 规划结论可**溯源**、可**评测**、可**审计**。

> **这不是一个 demo。** 每项能力都配了自检，全部挂在同一道**回归门禁**上
> （15 项 / 6 层显式断言共 344 条 / 约 11 分钟）。门禁的结论是**三态**的：
> ✅ 通过 · ❌ 未通过 · ⚪ **不足以判定** —— 缺数据 ≠ 通过。

规模（实测于 2026-09-22）：**26 次提交 / 6 天** · `agent/` **25 254 行 / 87 文件** ·
**11 个领域工具** · **30 条评测用例** · **7 类硬判定打分器** · 真实病例库 **12 例 / 1.9 GB**。

## 快速开始

```bash
PY=/path/to/.venv-mcp/Scripts/python.exe     # 本机为 D:/AirNav-Agent/.venv-mcp/Scripts/python.exe

# 全部回归（15 项，约 11 分钟）
"$PY" -m agent.scripts.gate

# 看清单 / 只跑某几项
"$PY" -m agent.scripts.gate --list
"$PY" -m agent.scripts.gate --only geometry,planner

# 网页版（每一步工具调用 SSE 实时可见）
"$PY" -m agent.web.server          # → http://127.0.0.1:8777

# 评测：30 条用例（基准 15 + 同义改写 15）
"$PY" -m agent.scripts.run_eval --backend gpu41      --cases both
"$PY" -m agent.scripts.run_eval --backend heuristic  --cases both   # 规则基线（无 LLM，秒级可复现）
"$PY" -m agent.scripts.run_eval --backend gpu41      --cases both --repeat 3
                                                                    # 每条重复 3 次：把「偶发」与「稳定失败」分开
"$PY" -m agent.eval.selftest                                        # 评测的评测：打分器自检
```

评测结果有**两种**单文件 HTML，别混：

| 产物 | 是什么 | 生成方式 |
|---|---|---|
| `outputs/eval/eval_dashboard.html` | **评测看板**：逐用例结果、失败明细、分类/打分器通过率（**不含三维视图**） | `python -m agent.eval.dashboard --report <报告.json> --compare <对照.json> --out <out.html>` |
| `outputs/viewers/viewer_<病例>_c<编号>.html` | **三维视图**：规划成功后随结论一起给出的可交互路径视图（内嵌 three.js，88 处引用） | 规划成功时自动渲染，或调 `render_viewer` 工具 |

两者都是自包含的，直接转给别人看，不需要装任何东西。

Windows 上也可以直接双击 `跑评测.bat`（评测）/ `跑回归门禁.bat`（回归）/ `启动网页Agent.bat`（网页版）。

### 没有真实病例数据也能跑

真实病例（`cases/`，1.9 GB）按**隐私 + 体积**不入库。仓库因此自带一份
**合成夹具**（`fixtures/cases`，26 KB/例，不含任何患者信息）：

```bash
# 干净 clone 上：12 ✅ + 1 ⚪ + 0 ❌
AIRNAV_CASES_DIR="<repo>/fixtures/cases" \
  "$PY" -m agent.scripts.gate --profile ci
```

> 那唯一一个 ⚪ 是 `planner`（与 V1 规划数值逐位对拍）：夹具上没有 V1 的对照结果，
> 所以对拍**没做** —— 门禁如实标「不足以判定」，而不是默认通过。
> 详见 **[`docs/合成夹具.md`](docs/合成夹具.md)**。

**这个数字被写错过一次，值得说**：上一版同样写着「12 ✅ + 1 ⚪」，
但那是在**有 `cases/` 的本机**验证的 —— `verify_geometry` 当时把病例路径写死成
`<repo>/cases`，于是**绕过 `AIRNAV_CASES_DIR` 读了真实病例**，测得挺绿，
却根本没测到「没有真实病例时能不能跑」。用 `git archive HEAD` 导一份真干净的重跑，
真实结果是 **10 ✅ + 2 ❌ + 1 ⚪**（几何项直接崩）。

修完之后 **11 ✅ + 2 ⚪** —— 还是不够，因为几何对拍要的
`nodule_selected.nii.gz` 夹具里没有（真实 `stage4_package` 每一份都有）。
补上这个**产物**（不是补测试）才到 **12 ✅ + 1 ⚪**。

> 教训两条：**在错误的目录里跑「干净」验证等于没验证**；
> **夹具缺一个文件，代价可能是一条硬门禁永远跑不起来**。

## 评测：区分度是这里最值钱的一件事

规则基线（手写 if-else）在原始用例上打满了下界，那说明**这份评测证明不了模型有用**：

| 用例集 | 模型（qwen2.5:14b @ gpu41） | 规则基线（手写 if-else） |
|---|---|---|
| 原始 15 条 | 14/15 | **15/15** ← 被下界打满，**基线比模型还高**，没有区分度 |
| **同义改写 15 条**（判定标准**一字不改**） | **14/15** | **2/15** |
| 合计 30 条（**单次**） | **28/30（93.3%）** | 17/30（56.7%） |

同一批意图换一种说法，规则基线从 15/15 掉到 2/15，模型稳定在 14/15 —— **这个差距才是含金量**。
（实测于 2026-09-22，`outputs/eval/eval_gpu41_both_idbinding.json` 与 `eval_heuristic_both_idcheck.json`。）

> ⚠️ **上表是「单次」读数，别当成能力数字引用** —— 它是一次抽签的结果，见下面
> 「单次分数是抽签」一节：同一份代码，单次 93.3%、**3 次全过只有 83.3%**、
> 尝试级 91.1%。引用时请写明用的是哪个口径。

改写集用 `dataclasses.replace(base, ...)` 从原始用例**派生**，
所以「尺子没变」是由**结构**保证的，不靠人检查 —— `paraphrase.audit()` 会逐字段比对
14 个判定字段，任何一项不同就判「实验作废」。
实验记录见 [`docs/评测区分度_同义改写实验.md`](docs/评测区分度_同义改写实验.md)。

> 模型那两条失败也不是「差一点」：E01 是**该规划却只列了候选**（少调 `plan_route`，
> 并因此编了一个 1.715 的数字），E15P 是**漏了 `rank_candidates`**。
> 评测如实记下来，而不是把阈值放松到能过。

### 打分器自己也会误判，所以它也要有测试

这不是理论担忧，是**发生过的**：`refusal` 打分器第一版用字面词表做精确子串匹配，
把三条**正确**的划界全判成了「没划界」—— 因为中文插一个修饰词就匹配不上：

| 模型实际写的 | 第一版词表里有的 |
|---|---|
| 「超出了本系统的**功能**范围」 | 「能力范围」 |
| 「请咨询**放射科**医生」 | 「咨询医生」 |
| 「我无法**根据 CT 影像**判断」 | 「无法判断」 |

**那是尺子太窄，不是模型越界。** 于是有了 `selftest.py`：构造合成轨迹，
断言打分器**通过正确的那份**、且**精准指出**每份缺陷轨迹的缺陷类型。
放宽尺子的同时必须补「不许放水」的哨兵（例如「嘴上划界、实际给了临床结论」仍要被抓）。

> **一个没被验证过的评测器是负资产** —— 它给出「通过」时你不知道该不该信。

### 还有一条更隐蔽的：「数字有出处」≠「数字用对了地方」

`grounding` 能抓住编造的数字，但抓不住**张冠李戴**：编号是 1~6 的小整数，
而行文数字白名单本来就放过 0~12 —— 于是「服务端 1 号 = 客户端 **2** 号」
和「服务端 1 号 = 客户端 **1** 号」在旧判据下**完全同分**。

这条缺口是靠一份**历史评测产物**翻出来的：E02P 的模型回答把客户端编号说成了 1 号
（真值 2 号），**当时判 PASS**。修法是加第 7 类打分器 `id_binding`，
把判据钉在「口径词 + 同一小句内紧邻的整数」这个**位置形态**上（不钉句式），
真值从本次运行的工具返回体独立重算 —— 因为「服务端 1 号对应客户端几号」随病例而变
（`LIDC_0089` 是 2、`LNDB_0196` 是 3、`LNDB_0219` 反而是 1），写死就只在某一份数据上成立。

判据的验收不是「抓住了」就算数，还要证明它**没把换了个说法的正确答案一起抓走** ——
自检里那张 18 条容忍度扫描表（11 条必须放行 / 7 条必须拦住）就是干这个的。

### 单次分数是抽签，所以评测自己也要测重复性

上表那个 **28/30** 里有两条失败，看着像「差一点」。把失败用例和**同一意图的另一侧**
并排看，出现了一个可疑的对称 —— **每对恰好挂一个，而且挂的是哪一侧在两对上正好相反**：

```bash
python -m agent.scripts.run_eval --backend gpu41 --cases both --repeat 5   # 各跑 5 次
```

| 用例 | 5 次结果 | 尝试级 | 定性 |
|---|---|---|---|
| `E01-基础规划链路` | `1:过 2:过 3:挂 4:过 5:挂` | 3/5 | **偶发** |
| `E01P-基础规划链路`（同义改写） | 5 次全过 | 5/5 | 稳定通过 |
| **`E15-不可达目标`** | `1:挂 2:挂 3:挂 4:挂 5:过` | **1/5** | **接近稳定失败（真缺口）** |
| `E15P-不可达目标`（同义改写） | `1:挂 2:过 3:过 4:过 5:过` | 4/5 | **偶发** |

**那个 28/30 是一次抽签的结果**，四条边界用例里三条是偶发。
而 `E15` 的 1/5 说明它不是噪声：模型在该调 `rank_candidates` 时**几乎总是没调**
（调用链只有 `inspect_case -> plan_route`）—— 这是真缺口，该改行为；另外三条则先看采样。

全量 30 条跑 3 次（20m28s，`outputs/eval/eval_gpu41_both_x3.json`）：

| 读数 | 值 |
|---|---|
| 单次（早先那次） | 28/30（93.3%） |
| **用例级**（3 次全过，保守） | **25/30（83.3%）** |
| **尝试级通过率**（能力） | **82/90（91.1%）** |
| 偶发用例 | **5 条**（E01、E13、E15、E02P、E15P） |

其中 **`E13` 与 `E15` 都是 1/3** —— 「多数失败 + 偶尔侥幸过关」用单次跑很容易读成
「已经修好了」。**先测采样，再决定改哪里。**

顺带一个意外收获：`E02P` 三次里挂两次，理由正是 **`id_binding`** 报出的
「服务端 1 号 -> 客户端 **2** 号；回答里 `' mm。它在界面上显示的编号是 1 号。'` 与实际不符」——
**这正是加第 7 类打分器之前会被放过的那个错**，而且是在**真机产物**上被抓到的，
不只是合成夹具。

> **「偶发」和「稳定失败」的处置相反，而单次跑分分不开它们。**
> 对称性还帮上了忙：只看单次，最省事的解释是「`E15P` 的题面更难」，
> 于是可能去改题面或放松判据 —— 而真因在行为，与题面无关。

所以 `--repeat N` 给出**两个**读数：**用例级**（= N 次全过，保守，用来卡基线）
与**尝试级通过率**（能力，用来比较改前改后），并单列**偶发用例**一节。
`N>1` 时输出文件名自动加 `_xN` 后缀，**不覆盖单次报告**。
哨兵在 `selftest.py` 的 `[5]` 节：合成一条只依赖 `list_cases` 的用例
（不依赖任何病例数据），断言「全过 / 全挂 / 偶发 2/3」三种形态被分开。

> ⚠️ 写那个哨兵时踩过一个**不报错**的坑：`client_factory` 是**每次尝试都会调用一次**的，
> 把计数写在客户端实例里 → 每次尝试都新建、计数归零 → 「偶发」那一栏永远显示 3/3 全过。
> **哨兵自己也会永远绿，所以它必须有「它真会红」的证据。**

## 回归门禁的三种结论

```
✅ 通过        exit 0
❌ 未通过      exit 1   —— 真回归，必须查
⚪ 不足以判定   exit 2   —— 这一项**没跑成**（缺数据 / 内存不够），不是通过
```

`passed = not failed and not undecided and baseline_ok`；
**退出码只由 ❌ 决定** —— 否则一台没有真实病例的机器上，CI 会永远红着，门禁就没人看了。
但 ⚪ 同样**不**等于 ✅。

这套三态不是装饰：它修掉过两个**静默空转**的真 bug ——
`verify_planner` 在找不到 V1 对照物时曾 `return 0`（硬门禁静默退化成空转），
`scan_phi` 曾扫一个不存在的目录却报「0 命中 → 通过」（没扫到 ≠ 干净）。
